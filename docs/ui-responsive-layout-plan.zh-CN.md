# WhisperMac 响应式布局改进方案

## 0. 文档用途与基线

- **用途：** 给后续 AI 或开发者直接执行的响应式布局改造计划；本文件本身不改变产品行为。
- **调查日期：** 2026-09-07。
- **代码基线：** `cf3760b`（`Rework main window into state-driven task workspace (P0)`），P0 任务工作区改版已完成。
- **前置文档：** [UI 改进执行计划](ui-improvement-plan.zh-CN.md)、[视觉与状态规格](ui-visual-spec.zh-CN.md)。本方案不推翻二者的信息架构与真实性约束，只处理"窗口尺寸变化 → UI 元素重排"这一维度；冲突处见 §2.3。
- **调查方式：** 静态审计 `Sources/whispermac` 全部布局相关代码（`ContentView.swift`、`MainWorkspaceViews.swift`、`WhisperMacApp.swift`），未启动 UI 实测；行号以基线提交为准。
- **评审修订：** 2026-09-07；修正几何 API 兼容性、滞回状态、弹性宽度验收、阅读列对齐与运行态高度预算，补充可复现验收口径。以下是待实施计划，不代表 UI 已验证。
- **结论性质：** 下文"现状"以代码为准；断点数值、居中阈值是项目设计选择，需在实现后按实际观感微调。

## 1. 问题定义与目标

**问题：** 窗口当前只有"最小尺寸"约束（980×720，`WhisperMacApp.swift:20`），向任意方向变大时 UI 几乎不重排——控件保持固定宽度、实时文本保持固定高度、阅读列始终左对齐，全屏时右侧留下大片空白。缩小方向则被最小尺寸完全禁止，不存在紧凑布局。

**目标（本轮）：**

1. 放大窗口时，表单控件、进度条在合理区间内弹性伸缩，不留单侧大空白（落实既有验收矩阵"更大窗口 1440×900 或更大"一行）。
2. 纵向放大时，实时文本区填充可用高度，而不是固定 260 pt。
3. 窄窗口与大字体叠加时，底栏与表单行自动换行/纵向堆叠，主动作永不裁切。
4. 建立可复用的窗口尺寸观察基础设施（宽度档位 + 滞回），为后续紧凑模式铺路。

**非目标（本轮不做）：**

- 不降低最小窗口 980×720。860×640 紧凑模式、队列折叠是原计划 P2 的独立可行性评估，本方案只准备基础设施（R6），不实现。
- 不改转写引擎、批处理语义、状态合同（`TaskPresentation`）与任何文案语义。
- 不重做信息架构：三层骨架（工具栏 / 队列+工作区 / 底栏）不动。
- 不引入第三方布局库；布局优先使用 SwiftUI。现有 AppKit 桥接可用于 DEBUG 窗口控制与必要的原生 sheet 尺寸适配。

### 2.3 规格协调与本方案采用的设计

- `ui-visual-spec.zh-CN.md` §7.1 要求保留阅读宽度与呼吸空间，但没有明确规定整列必须左对齐；当前实现选择了左对齐。
- `ui-improvement-plan.zh-CN.md` §8 要求大窗口不留下无意义的大空白。两者可以通过限制阅读宽度、对称分配留白共同满足。

**本方案采用：** `expanded` 档位下阅读列居中，上限从 760 提至 820 pt；列内文字和表单仍左对齐。R5 实施时同步更新视觉规格 §7.1 的尺寸、对齐与底栏高度说明。本次只修订执行方案，不宣称已完成规格同步或 UI 改造。

### 2.4 明确不改的"固定"（是规格决策，不是缺陷）

- 四种输出格式固定 2×2 两行（视觉规格 §4.1 明确"不把四个选择硬挤在单行"）。宽窗口不改为单行四列。
- 队列行高约 64 pt、工具栏设计高度约 64 pt 保持既有设计；底栏 80/96 pt 改为最小高度（R3），内容放不下时允许增长。原生工具栏实际占用高度以测量为准，不用于写死运行态高度预算。
- 底栏进度条 18/82 估算映射与文案语义（本方案只动宽度，不动数据）。

## 3. 响应式策略

### 3.1 两条机制，按序使用

1. **连续弹性（首选）：** `minWidth/idealWidth/maxWidth` 区间 frame、flexible 栅格、`ViewThatFits`。同一布局候选内控件随可用宽度连续变化，无需档位状态；`ViewThatFits` 的横排/纵排切换允许一次结构变化。适用于单行控件、进度条、标签列。
2. **离散档位（兜底）：** 只用于**结构性**重排——阅读列左对齐→居中（R5）。档位必须带**滞回**（进入和退出阈值不同），避免 live resize 时在阈值附近来回抖动。

`ViewThatFits` 按候选视图在指定方向上的 ideal size 选择布局。纵向 `ScrollView` 提供的是自身可用宽度，经过队列、阅读列和 padding 后通常小于窗口宽度，更不是屏幕宽度。固定标签 frame、可压缩文字或无限宽包装都可能掩盖真实溢出；必须验证候选内容是否完整，不能仅凭采用该 API 判定自适应已成立。

`idealWidth` 仅补充未指定宽度的提案，不是“980 窗口下的默认宽度”。本方案允许最小窗口下控件宽度与基线不同，只要求功能、信息层级和可用性不回归；不引入额外宽度公式来追求像素级一致。控件到达上限后可以停止增长。

### 3.2 技术选型（macOS 14 约束）

- 部署目标是 **macOS 14**（`Package.swift:9`）。使用包含该 API 的 SDK 构建时，`onGeometryChange(for:of:action:)` 的 **action 仅接收 newValue** 重载支持 macOS 13 起；接收 oldValue/newValue 的重载要求 macOS 15。优先使用单参数重载，实施时确认 CI 构建 SDK；若工具链不提供该 API，则用 background 中的 `GeometryReader` + preference/onChange 回退，不新增占据布局空间的根容器。
- 在 `mainWorkspace` 外层填满剩余空间的容器上观察宽度，位置在阅读列限宽之前。不要用窗口宽减写死的队列宽作为实现，也不要观察已经限宽到 760/820 的内容自身。
- 档位保存于 `ContentView` 的视图本地状态，不存入 `AppModel` 或持久化设置；几何回调中转换，只有档位改变时写入状态，不在 `body` 求值中写状态。当前 `.id(model.appLanguage)` 标记的是内部视图树，不能据此认定 `ContentView` 的所有 `@State` 都会重置；语言切换后验证观察器能重新获得实际宽度。
- 本轮不新增窗口尺寸持久化；恢复窗口、首次打开和全屏退出时都重新读取实际几何。

### 3.3 尺寸口径与宽度档位

本方案的 980×720、1120×800、1440×900 均指 **ContentView 根布局区域的逻辑 pt 尺寸**，不指 `NSWindow.frame` 外框、不指截图像素。980×720 来自现有根视图最小 frame；全屏记录实际测量值，不强求屏幕标称尺寸等于根布局尺寸。

档位基于工作区外层实际可用宽度，包含阅读列 padding、不包含队列。按当前队列 236 pt 和约 1 pt 分隔线估算，根宽 980/1440 时工作区约 743/1203 pt；该减法仅用于说明。

纯函数接口：`WindowSizeMode.next(current: WindowSizeMode?, workspaceWidth: CGFloat) -> WindowSizeMode`。

| 当前状态 | 输入宽度 | 下一状态 |
| --- | --- | --- |
| 尚未初始化（nil） | ≥1100 / <1100 | expanded / regular |
| regular | ≥1100 / <1100 | expanded / regular |
| expanded | <1060 / ≥1060 | regular / expanded |

- 1060–1100 pt 区间内保留上一档位；恰好 1060 保留 expanded，恰好 1100 进入 expanded。
- 首次有效测量前以 regular 渲染；非有限值或非正宽度忽略，保留当前状态（未初始化时仍为 nil）。有效测量后才调用纯函数。
- regular 阅读列上限 760、整列左对齐；expanded 上限 820、整列居中。40 pt 滞回避免阈值附近重复切换，不会消除一次切换时的位置变化。
- 常量放入 `TaskWorkspaceMetrics`。初值需实测微调；调参时同步转换测试和验收阈值。

## 4. 改造项

### R1 工作区尺寸观察基础设施（纯地基，无视觉变化）

- 按 §3.2 在工作区外层观察宽度，并使用 §3.3 的状态转换函数；环境键对下游提供已解析的 regular/expanded，初始化前默认 regular。
- 测量源必须独立于档位应用结果，避免“列变宽 → 测量改变 → 档位再次改变”的反馈。仅保存档位，不为 R1 保存逐像素变化的窗口宽度。
- 新增 `WindowSizeMode` 环境键与 `readingColumnMaxWidthExpanded = 820` 等常量。
- **验收：** `swift build` + `WindowSizeModeTests`；测试初始化、743/1203 典型值、1059/1060/1099/1100 边界，以及 `1059 → 1100 → 1080 → 1060 → 1059` 双向序列。相同 1080 输入分别从 regular/expanded 开始必须得到不同结果。实机确认语言切换、窗口恢复后档位正确，R1 本身无视觉变化。

### R2 表单控件弹性化与行布局验证

- 把固定 `width` 换成区间 frame：
  - 输出位置 Menu `width: 380` → `minWidth: 320, idealWidth: 380, maxWidth: 560`；
  - 语言 Picker `width: 240` → `minWidth: 200, idealWidth: 240, maxWidth: 360`；
  - 下载进度条 `width: 280` → `minWidth: 220, idealWidth: 280, maxWidth: 420`；
  - 结果选择器保持 `maxWidth: 460` 不变。
- 先修正并验证 `LabeledRow`：横排标签应参与自然宽度测量，104 pt 作为基准列宽，不能通过固定 frame 把过长标签伪装成“放得下”。必要时为横排标签保留水平自然尺寸；纵排标签允许换行。验证长标签、长路径和控件最小宽度叠加时确实选择纵排，再迁移 `defaultsRow`（`:238`）与 `snapshotRow`（`:686`），删除私有 120 pt 标签列。保留原有颜色、字体、路径截断及完整值访问方式。
- `SettingsSheet`：`pathRow`、语言行迁移到 `LabeledRow`；segmented Picker `width: 280` → `maxWidth: 320`（segmented 控件不宜拉伸过宽，保持上限）。
- **验收：** 980 宽时信息与操作完整，允许控件比原来更宽；拖宽时未达到上限的控件可增长，达到上限后保持稳定。按 §6 的真实文字缩放检查 EN/ZH/JA，只有横排放不下时才要求纵排，不要求所有行在 1.2× 下强制切换。固定宽度的设置 sheet 也必须覆盖。

### R3 底栏自适应重排

- 进度条 `width: 220` → `minWidth: 140, idealWidth: 220, maxWidth: 320`。
- `runningLeading` 阶段标题加 `lineLimit(1...2)` + `truncationMode(.middle)`；进度 caption 保持单行截断。
- `PersistentActionBar` 的 `HStack { leading; Spacer; trailing }` 包 `ViewThatFits(in: .horizontal)`：放不下时退化为两行 VStack（状态行在上、按钮行在下），底栏高度在堆叠态自动增高（改 `minHeight` 语义：80/96 变为 `minHeight`，去掉 `maxHeight` 钉死）。
- 横排候选应让按钮使用自然尺寸，文字可按上述规则截断；不能依靠压缩按钮文字制造“放得下”的结果。纵排按钮行若仍放不下，要提供按钮纵排兜底并保留主动作优先级；底栏增加上下 padding，不能只有 minHeight 而让堆叠内容贴边。切换条件由实际内容宽度决定，不绑定 1.2× 或某种语言。
- **验收：** 980×720 默认文字下无操作回归；三语、长文件名、失败摘要和下载状态均检查。大字体下按钮文字完整、状态不重叠；每个布局候选的临界宽度两侧拖动不振荡。底栏真实高度必须参与 R4 的可用空间计算。

### R4 运行态纵向弹性（保留高度不足时的滚动兜底）

**采用保守实现：保留页面级 `ScrollView`，动态分配内层实时文本高度。** 空间充足时整页恰好填满，不产生外层滚动；空间不足时页面允许滚动，底栏始终在页面之外。不要直接换成无滚动兜底的 VStack。

- 从工作区外层测得可用高度 `H`（已经扣除底栏），测量当前列宽下所有非文本视口内容的实际高度 `F`：标题/副标题、展开或收起的任务详情、实时文本标题、分隔线、跟随开关行、全部 spacing 和 padding。
- 视口高度为 `max(240, H - F)`。测量不得包含动态视口自身；每项 spacing/padding 仅计一次，避免自反馈。首个有效测量前使用 240 pt，非有限测量忽略。`F` 必须在宽度、字体、语言、详情展开状态变化后更新，不以固定 250 pt 代替。
- 等待占位和有片段的滚动视口共用这一高度。空间不足时 `F + 240 > H`，由真实存在的外层 ScrollView 承担溢出；不抬高根窗口最小高度，不强制收起详情，不增加副标题单行限制。
- 保持同一个 `ScrollViewReader`/转写视图实例与 `followsLatest` 状态，尺寸变化不得通过 `.id` 或两个替代布局副本重置它们。跟随开关位于视口下方，空间足够时贴近页面底部，降级时通过外层滚动可达。
- **验收：** 980×720 与宽而矮的 1440×720 都检查详情展开/收起、长文件名及输出路径、1.2× 字体、底栏堆叠；所有内容和开关可达，窗口仍能回到最小尺寸。拉高时视口增大，到足够高度后外层无多余滚动。分别验证鼠标滚轮/触控板的内外滚动与键盘访问。
- 开启跟随时新增片段仍滚到底；关闭跟随后新增片段、拖动尺寸及切换高度降级状态不强制跳到底，阅读位置尽量保持。切换后跟随开关值不变。本轮保留嵌套滚动这一权衡，不把彻底移除嵌套滚动列入完成条件。

### R5 大窗口阅读列居中 + sheet 可调（依赖 R1）

- 公共 modifier `readingColumn(_ mode: WindowSizeMode)` 必须接管现有**两级 frame**，替换旧的两级包装，不能只改内层 alignment：

```swift
content
    .frame(maxWidth: mode == .expanded ? 820 : 760, alignment: .leading)
    .frame(maxWidth: .infinity,
           alignment: mode == .expanded ? .center : .leading)
```

- 上限沿用现有口径，包含阅读列内部左右各 32 pt padding；列内文字始终 leading。测量工作区的容器在 modifier 外部。四个工作区采用相同规则。
- 日志 / 历史 / 全部输出 sheet 将固定尺寸改为最小尺寸（分别 680×500、560×440、620×440），并保留原尺寸作为初始布局目标。内部列表/日志随 sheet 增长，操作行始终可达。设置 sheet 保持宽 640，内容增高时需可滚动。
- “改 minWidth/minHeight”只是实现起点，不等于原生 sheet 已可拖拽。先在 macOS 14 和当前开发系统验证边缘拖拽、最小尺寸、关闭重开及父窗口调整；若 SwiftUI 默认宿主不支持目标行为，限于 sheet 的 AppKit 适配作为后备，保留现有模态语义，不悄悄改为独立窗口。先做一个日志 sheet 验证，再推广另外两个。

## 6. 验收矩阵与复现方法

### 6.1 测量与输入准备

- **尺寸：** 为现有 DEBUG 驱动新增 `resize-content:<w>x<h>`，目标是 §3.3 定义的根布局尺寸。AppKit 内容区和根布局可能因工具栏、安全区域而不同：通过内容尺寸 API 或内容矩形转 frame 发起调整，再读取根布局实际尺寸验证；必要时校正差值。不得直接把目标数字传给 `window.setFrame` 就宣称达标。
- **测量记录：** 每张截图旁记录目标/实际根布局尺寸、工作区尺寸、档位、底栏高度、转写视口高度、语言、外观、字体设置、详情展开状态。布局稳定后再截图；截图像素可因显示缩放不同而变化。屏幕空间不足时记录系统实际限制，不伪造目标尺寸通过。
- **字体：** 1.2× 指实际排版字体的点数放大，不能只设置 `dynamicTypeSize`，也不能用 `scaleEffect` 放大最终画面。准备仅 DEBUG 可用的字体缩放输入（例如 `WHISPERMAC_UI_FONT_SCALE=1.2`）：通过共享字体构造入口将被验收的显式 `.system(size:)` 点数乘以比例，语义字体与按钮/Picker 标签也要有明确缩放路径。默认系数为 1，发布版无可调入口。记录覆盖的控件；未被缩放的原生控件必须单独说明，不能算已验证。
- 字体压力测试之外，单独测试 `dynamicTypeSize >= .xLarge` 的底栏分支，以及目标 macOS 可用的系统文字设置。DEBUG 缩放通过不代表系统文字设置的生产支持已自动完成；若系统设置不能改变预期文字，记录为字体适配缺口，不宣称通过。
- **内容：** 使用长中文/日文标签、至少 100 字符的文件名、长输出路径、多文件、长失败摘要，覆盖下载、准备、转写、停止中、成功、失败、取消。准备阶段的文件名和展开详情是必要样例。
- **状态：** 优先使用现有 DEBUG 驱动和可复现媒体输入。短暂状态可增加仅 DEBUG 的展示夹具，不改变发布版状态合同；夹具截图只能验证布局，自动跟随/停止等行为仍用实际任务验证。

## 7. 风险与注意

- **高度反馈：** R4 的 `F` 只测非视口内容；视口高度变化不应反过来改变被测对象。宽度、字体和详情展开引发的真实高度变化需要重新测量；连续相同测量不要重复写状态。
- **底栏增长：** 80/96 是下限，不是堆叠后的预测高度；状态长短和按钮数量也可能触发堆叠。R4 从工作区取得真实剩余高度，不手动假设底栏只多 16 pt。
- **嵌套滚动：** 本轮为高度不足保留外层滚动。重点验证滚轮、触控板、键盘和自动跟随的相互作用；后续若重构为单滚动容器，须单独验证阅读位置和流式更新。
- **候选布局误判：** `ViewThatFits` 不保证固定 frame 内文字完整。先修正横排测量，再验收纵排；以控件内容是否完整为准。滞回只用于阅读列档位，不能替代候选布局自身的实机边界检查。
- **大字体：** DEBUG 实际字体缩放与系统设置是两条独立证据。默认字号的基线截图需复查，防止引入字体辅助入口时改变正常外观。
- **居中与原型：** 原型仍可保留为历史设计参考，但 R5 必须同步视觉规格并附实际截图，不能把旧原型当作已验证效果。
- **语言与身份：** 观察器保持在稳定的工作区外层；语言切换后复测几何，不把整个 ContentView 的状态重建作为正确性的前提。
- **sheet 平台差异：** 先验证日志 sheet，确保目标系统实际允许 resize 后再推广；最小 frame 声明本身不是验证证据。
- **不改引擎边界：** 本方案不应触碰 `WhisperInvocation.swift`、`TranscriptionService.swift`、`RuntimeModelResolver.swift`；布局问题应在视图层解决。

## 8. 完成定义

从根布局 980×720 拖到全屏：控件在区间内弹性伸缩并遵守上限，实时文本利用剩余高度；高度不足时能通过页面滚动访问全部运行信息和跟随开关；大窗口整列居中、列内内容左对齐；底栏必要时堆叠且主动作完整可见。最小窗口保持功能可用，不要求像素级宽度一致。详情展开、长文本、大字体、底栏增高叠加时仍可回到最小窗口。

档位双向序列测试通过，语言切换与尺寸恢复正确，三个内容型 sheet 在目标系统实际可拖拽，R5 规格同步完成，§6 实机证据齐全。RA6 只交付紧凑模式评估，不降低产品最小尺寸。未执行的最低系统或字体场景明确列为未完成验收项。

## 9. API 核验依据

- [Apple：frame(minWidth:idealWidth:maxWidth:minHeight:idealHeight:maxHeight:alignment:)](https://developer.apple.com/documentation/swiftui/view/frame(minwidth:idealwidth:maxwidth:minheight:idealheight:maxheight:alignment:))：ideal 尺寸补充未指定的提案维度，不能用来保证特定窗口宽度下的控件尺寸。

### 10.5 R6 紧凑模式（860×640）评估结论

**可行，建议作为独立 P2 任务包立项**，改动集中在 `TaskWorkspaceMetrics`（新增 `compact` 档与队列折叠状态）与 `MainWindowContent`，不触碰状态合同与服务层。估算：860 窗口 → 工作区 623 pt → 内容列 559 pt；就绪表单横排行（104 标签 + 16 + 自适宽 Menu ~200）≈ 320 pt 放得下，大字体由 `LabeledRow` 纵排兜底；运行态底栏在堆叠候选下主动作完整可见；高度 640 − 底栏 80 = 560，运行态固定区块 ≈ 284 pt，实时文本仍得 ~276 pt ≥ 240 下限（R4 的滚动兜底进一步降低风险）。需补组件：队列折叠（工具栏开关 + 持久化 + 折叠时主区/底栏不跳动，注意 §R6 提示的"折叠→可用宽度增大→又自动展开"反馈）与紧凑档工具栏图标化；`List` 嵌套滚动与 48 pt 紧凑行需实机走查。
